# Yosakoi Data Manager 憲章

## 基本原則

### I. ソースデータ完全性
生のソースファイルは、リポジトリにコミットされた後は不変でなければならない。
すべての変換処理は、入力ファイル、出力ファイル、スキーマに関する前提をコードまたは
隣接するドキュメントに明示し、他の貢献者が任意の出力レコードを元データまで追跡
できる状態を保たなければならない。変換処理がソースデータを補正する場合、その補正は
記録されていない手作業ではなく、文書化された正規化ステップとして表現しなければ
ならない。理由: 本プロジェクトはデータを管理するためのものであり、出力への信頼は
来歴を保持できることに依存するため。

### II. スクリプト化され再現可能な運用
データの取り込み、正規化、検証、出力は、明示的な引数を持つ、リポジトリに含まれた
スクリプトまたはコマンドを通じて実行しなければならない。表計算ソフトだけに依存した
手作業のワークフロー、その場限りのシェル編集、記録されていないローカル手順を、
成果物を生成する唯一の方法にしてはならない。生成される出力は、リポジトリの状態と
宣言済みの入力から再作成できなければならない。理由: 再現性は保守、レビュー、
引き継ぎの前提条件であるため。

### III. マージ前の検証
振る舞いを変える変更には、修正または機能追加の前には失敗し、変更後には成功する
自動検証を必ず含めなければならない。パース規則、スキーマ変換、出力形式は、代表的な
境界条件を扱うテストまたはフィクスチャベースの検証でカバーしなければならない。
自動検証できない変更には、機能成果物内に文書化された手動検証手順を必ず含める。
理由: データの不具合は静かに混入しやすく、広がる前に捕捉する必要があるため。

### IV. 安全かつ冪等なファイル操作
ファイルを作成、上書き、改名、削除するコマンドは、その影響を明示し、再実行しても
安全でなければならない。破壊的な操作には、ドライラン機能、バックアップ戦略、
またはその操作自体が本質的に安全である理由の文書化のいずれかが必要である。
出力パス、競合時の挙動、文字エンコーディングの前提は、コードまたはドキュメントで
定義しなければならない。理由: データ作業ではバッチの再実行が通常であり、安全でない
ファイル操作は回復不能な損失を招くため。

### V. クリーンコードと保守性
本番コードは、読みやすく安全に変更できるように構成しなければならない。関数と
モジュールは単一で明確な責務を持ち、名前は意図を伝え、重複は挙動を見えにくくしたり
変更リスクを高めたりする場合に排除しなければならない。コメントはコードの言い換え
ではなく、暗黙的でない設計判断を説明するために使う。より小さく検証可能な
リファクタリングで同じ結果を得られる場合、中間の安全確認を伴わない大規模な
書き換えは避けるべきである。理由: 保守性は単なるスタイルの好みではなく、成果物の
品質要件そのものであるため。

### VI. 観測可能な出力と意思決定の記録
自動化処理は、件数、警告、スキップされたレコード、失敗理由など、実務で利用可能な
検証結果を必ず出力しなければならない。形式に関する判断、フィールド対応、既知の
データ制約は、下流での解釈に影響する場合、該当する spec、plan、quickstart、
またはコードコメントに記録しなければならない。理由: 保守担当者には、迅速な
診断手段と、データセットが現在の挙動に至った理由の永続的な記録が必要であるため。

## 運用上の制約

- 標準的なワークフローでは、機能仕様で別形式を明示的に承認しない限り、UTF-8 の
  テキスト形式とファイルベースのインターフェースを優先しなければならない。
- 機能計画には、信頼できる入力ソース、期待される出力成果物、不可逆な変換境界を
  文書化しなければならない。
- 機能のために追加する依存関係は、その目的を達成するための最小限のツールチェーンと
  比較した正当化が必要である。
- 秘密情報、認証情報、非公開のソースデータをコミットしてはならない。spec と
  quickstart には、機微な入力をローカルでどう与えるかを記述しなければならない。

## 開発ワークフロー

- すべての機能は、データソース、変換手順、検証戦略、運用コマンドを特定する
  `spec.md`、`plan.md`、`tasks.md` から開始しなければならない。
- 実装計画の Constitution Check では、設計作業が調査段階を超えて進む前に、6つの
  基本原則すべてへの適合を確認しなければならない。
- タスク分解には、各ユーザーストーリーに対する検証作業を含め、ストーリー作業を
  始める前に必要な共通の検証、保守性対応、移行手順を明示しなければならない。
- スクリプト化されたワークフローを迂回する変更、来歴情報を欠く変更、安全策のない
  破壊的操作を導入する変更、または文書化された理由なくコードの明瞭性を下げる変更は、
  レビューで却下しなければならない。

## ガバナンス

この憲章は、このリポジトリ内で矛盾するローカル慣行に優先する。改定には、文書化
された根拠、影響を受けるテンプレートの更新、そして Sync Impact Report への
セマンティックバージョン判断の記録が必要である。バージョン方針は以下のとおりと
する。互換性のないガバナンス変更または原則削除は MAJOR、新しい原則の追加または
要求の実質的な強化は MINOR、既存の意味を保った明確化は PATCH とする。すべての
計画とプルリクエストには適合レビューが必要であり、レビュアーは承認前に憲章ゲート、
必要な検証成果物、宣言された例外を確認しなければならない。
