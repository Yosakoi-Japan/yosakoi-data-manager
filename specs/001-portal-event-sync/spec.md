# 機能仕様書: Yosakoi Portal イベントデータ連携

**機能ブランチ**: `001-portal-event-sync`  
**作成日**: 2026-04-29  
**状態**: 下書き  
**入力**: ユーザー要望: 「Yosakoi Portal のイベントデータ連携の仕組みを作りたい。技術スタックは後で決めるので、まず『何を作るか』を仕様書（spec）としてまとめてください。」

## 目的（Why）

- Googleスプレッドシートで管理しているイベント情報を、Yosakoi Portal に自動反映する。
- 手動で CSV を更新する作業を減らす。
- 承認済みのイベントだけをユーザーに表示する。
- データ管理とフロントエンド表示の責務を分離する。

## 仕様確認事項

### 2026-04-29 の確認

- Q: 何をもって「変更あり」と判定するか？ → A: `Approved` のみを抽出し、新規 `event_id` は新規保存、既存は `updated_at` と保存済みデータを比較して新しい場合のみ上書きする。
- Q: `updated_at` が無い・不正な場合はどう扱うか？ → A: 更新しない。
- Q: 同じ `event_id` が複数ある場合はどう扱うか？ → A: その ID のイベントはエラー扱いで対象外にする。

## ユーザーシナリオとテスト

### ユーザーストーリー1 - 承認済みイベントの公開データ生成（優先度: P1）

運営担当者として、管理元にあるイベント情報から承認済みのイベントだけを公開用データ
として出力したい。これにより、ユーザーに表示されるイベント情報を信頼できる状態に
保てる。

**優先理由**: 公開対象の絞り込みと出力生成は、この機能の中核価値であり、
最小実用機能として成立するため。

**独立テスト**: 管理元データに承認済み・未承認・却下済みのイベントを混在
させ、出力には承認済みイベントだけが含まれることを確認する。

**受け入れシナリオ**:

1. **Given** 管理元に `Approved` とそれ以外の状態のイベントが混在している、
   **When** 公開データ生成処理を実行する、**Then** 出力には `Approved` の
   イベントだけが含まれる。
2. **Given** 承認済みイベントに公開用データとして必要な項目が存在する、
   **When** 公開データ生成処理を実行する、**Then** `Approved` のイベントだけが
   Google スプレッドシートの管理元と同じ列構成の CSV 形式で出力される。

---

### ユーザーストーリー2 - 変更がある場合のみ反映する（優先度: P2）

運営担当者として、公開対象データに変更があった時だけ Yosakoi Portal に反映したい。
これにより、不要な更新処理や無意味な配信を避けられる。

**優先理由**: 自動化だけではなく、差分がある時だけ反映することが運用効率と
安全性の両面で重要であるため。

**独立テスト**: 同じ入力データで 2 回連続実行した時に 2 回目は更新されず、
入力データを変更した後は更新されることを確認する。

**受け入れシナリオ**:

1. **Given** 前回反映済みの公開データと今回生成した公開データが同一である、
   **When** 反映処理を実行する、**Then** 更新は行われず、変更なしとして扱われる。
2. **Given** 公開対象データに変更がある、**When** 反映処理を実行する、
   **Then** 変更がある場合に限り Yosakoi Portal へ反映される。
3. **Given** `Approved` の公開対象イベントのうち、`event_id` が保存済みデータに
   存在しない、**When** 反映処理を実行する、**Then** そのイベントは新規データ
   として保存される。
4. **Given** `Approved` の公開対象イベントの `event_id` が保存済みデータに存在する、
   **When** `updated_at` と保存済みデータを比較する、**Then** 新しい場合に限り
   既存データを上書きする。
5. **Given** `Approved` の公開対象イベントで `updated_at` が不正である、
   **When** 反映判定を行う、**Then** そのイベントは既存データを上書きしない。
6. **Given** 同じ `event_id` の `Approved` イベントが複数存在する、**When** 公開
   判定または更新判定を行う、**Then** その ID のイベントはエラー扱いで対象外になる。

---

### ユーザーストーリー3 - 定期実行と手動実行の両立（優先度: P3）

運営担当者として、更新処理を定期実行でき、必要時には手動でも実行したい。これにより、
日常運用は自動化しつつ、緊急修正や確認時にも即座に対応できる。

**優先理由**: 実運用では定期反映と運営判断による即時反映の両方が必要になる
ため。

**独立テスト**: 定期実行の設定に基づく実行と、担当者による明示的な手動実行の
両方で、同じ公開データ生成・反映ルールが適用されることを確認する。

**受け入れシナリオ**:

1. **Given** 定期実行のタイミングが到来している、**When** 更新処理が開始される、
   **Then** 通常の更新ルールに従って公開データ生成と反映判定が行われる。
2. **Given** 運営担当者が手動実行を開始する、**When** 更新処理が実行される、
   **Then** 定期実行と同じ基準で公開データが生成・反映される。

## 受け入れ条件（AC）

- 管理元データから公開対象データを取得できること。
- `status = Approved` のイベントだけが公開対象になること。
- 未確認・作業中・却下のイベントは公開データに含まれないこと。
- 公開対象データは、Google スプレッドシート管理元と同じ列構成の CSV 形式で
  出力されること。
- `Approved` の公開対象イベントについて、未保存の `event_id` は新規保存されること。
- 既存の `event_id` は `updated_at` と保存済みデータを比較し、新しい場合のみ
  上書きされること。
- `updated_at` が不正な既存イベントは上書きされないこと。
- 同じ `event_id` の `Approved` イベントが複数存在する場合、その ID のイベントは
  エラー扱いで対象外になること。
- 定期実行と手動実行の両方で同じ判定・出力ルールが使われること。
- データの編集や承認処理は管理元で完結し、本機能では行わないこと。

### エッジケース / 失敗時の挙動

- 管理元データに `Approved` のイベントが 1 件もない場合、空の公開データを返し、
  「公開対象なし」と分かる結果を出力する。未承認イベントは公開しない。
- `status` が空欄、不正値、表記ゆれの場合、そのイベントは公開対象に含めず、
  問題として識別できる結果を残す。
- 公開対象イベントに必要項目の欠落がある場合、不完全なデータをそのまま公開せず、
  該当イベントを除外または処理失敗として扱う。
- 管理元データの取得に失敗した場合、前回公開済みデータを不意に消したり上書きしたり
  しない。
- 変換失敗または CSV 書き込み失敗が発生した場合、既存の `yosakoi_festival.csv` は
  変更しない。
- 変更判定に必要な前回データが存在しない初回実行時は、初回反映として処理する。
- 手動実行と定期実行が近接した場合でも、同一データに対する不要な重複反映を避ける。
- 同じ `event_id` であっても `updated_at` が保存済みデータ以下である場合は、
  上書きしない。
- `updated_at` が不正値である既存イベントは、上書きせずにスキップする。
- `end_date` が現在日付より前のイベントは、公開判定および更新判定の対象外とする。
- 同じ `event_id` の `Approved` イベントが複数ある場合、その ID のイベントは
  重複エラーとしてスキップし、重複件数と対象 ID を確認できるようにする。

## 要求（Must / Should / Could） *(mandatory)*

### 機能要求

#### Must（必須）

- **FR-001**: システムは、イベント情報の管理元から公開対象判定に必要なデータを取得
  しなければならない。
- **FR-002**: システムは、`status = Approved` のイベントだけを公開対象として抽出
  しなければならない。
- **FR-003**: システムは、未確認・作業中・却下など `Approved` 以外の状態の
  イベントを公開対象から除外しなければならない。
- **FR-004**: システムは、公開対象イベントをフロントエンドで利用できる CSV 形式に
  変換しなければならず、その列構成は Google スプレッドシート管理元と同一で
  なければならない。
- **FR-005**: システムは、今回生成した公開データと前回反映済みデータを比較し、
  `Approved` の公開対象イベントについて、未保存の `event_id` は新規保存し、
  既存の `event_id` は `updated_at` と保存済みデータを比較して新しい場合のみ
  上書きしなければならない。
- **FR-005a**: システムは、既存イベントの `updated_at` が不正な場合、
  そのイベントを上書きしてはならない。
- **FR-005b**: システムは、`end_date` が現在日付より前のイベントを、
  公開判定および更新判定の対象外として扱わなければならない。
- **FR-005c**: システムは、同じ `event_id` の `Approved` イベントが複数存在する場合、
  その ID のイベントを重複エラーとして対象外にし、重複件数と対象 ID を運営担当者が
  確認できるようにしなければならない。
- **FR-006**: システムは、定期的に更新処理を実行できなければならない。
- **FR-007**: システムは、必要に応じて運営担当者が手動で更新処理を実行できなければ
  ならない。
- **FR-008**: システムは、データ編集や承認状態の変更を行ってはならず、公開用データ
  の取得・抽出・変換・反映だけを担当しなければならない。
- **FR-009**: システムは、取得失敗や変換失敗が発生した場合、未検証のデータで公開
  状態を更新してはならない。取得失敗、変換失敗、CSV 書き込み失敗のいずれでも、
  既存の `yosakoi_festival.csv` を変更してはならない。

#### Should（推奨）

- **FR-010**: システムは、更新処理の結果として、取得件数、公開件数、除外件数、
  変更有無を確認できる状態にすべきである。
- **FR-011**: システムは、公開対象外となった理由を運営担当者が追跡できるように
  すべきである。

#### Could（任意）

- **FR-012**: システムは、手動実行時に対象データの確認のみを行い、反映は行わない
  確認モードを提供してもよい。

### 主要エンティティ

- **管理元イベント**: 管理元で保持される元データ。公開可否判定に必要な属性と、
  フロントエンド表示用に変換される属性を持つ。
- **開始日 / 終了日**: `start_date` と `end_date`。`end_date` が現在日付より前の
  イベントはチェック対象外となる。
- **公開対象イベント**: 管理元イベントのうち `status = Approved` を満たし、
  公開対象として抽出されたイベント。
- **公開用 CSV**: フロントエンドが利用するために整形された出力データ。
  列構成は Google スプレッドシート管理元と同一とする。
- **event_id**: 公開対象イベントの同一性を判定する主キーとして扱う識別子。
- **event_name**: 表示用のイベント名称。
- **重複エラー**: 同じ `event_id` の `Approved` イベントが複数存在するため、
  公開判定または更新判定の対象外になる状態。
- **反映履歴**: 前回反映済みデータとの比較や、変更有無の判定に使われる基準情報。
  Git 管理された公開用 CSV を比較元として扱う。

## データの出所と運用

- **正本入力**: Google スプレッドシートを含むイベント情報の管理元データ。
  データの編集と承認は管理元で行う。
- **変換概要**: 管理元データを取得し、承認済みイベントのみ抽出し、
  Google スプレッドシート管理元と同じ列構成の CSV に変換する。`end_date` が
  現在日付より前のイベントは対象外とする。反映時は、Git 管理された既存の公開用 CSV
  を比較元とし、未保存の `event_id` を新規保存し、既存の `event_id` は `updated_at` を
  比較して新しい場合のみ上書きし、`updated_at` が不正な場合は上書きしない。
  同じ `event_id` の `Approved` イベントが複数存在する場合は重複エラーとして対象外にする。
- **再現手順**: 更新処理は定期実行と手動実行の両方で同じ仕様に従って
  再実行できること。
- **ファイル安全性**: データに変更がない場合は公開データを不要に更新しない。
  取得失敗や変換失敗時は Git 管理された既存の公開 CSV を不意に壊さない。
- **観測可能な出力**: 取得件数、承認済み件数、除外件数、出力件数、変更有無、
  失敗理由、過去開催のため対象外となった件数、重複エラー件数を運営担当者が
  確認できること。

## 成功基準

### 測定可能な成果

- **SC-001**: 承認済みでないイベントが公開用データに含まれる件数が 0 件である。
- **SC-002**: 同一データで更新処理を再実行した場合、不要な反映が発生しないことを
  100% のケースで確認できる。
- **SC-005**: 同じ `event_id` の既存データに対して、`updated_at` が新しくない
  データで上書きされる件数が 0 件である。
- **SC-006**: `end_date` 終了済みのイベントが更新対象として処理される件数が 0 件である。
- **SC-007**: 同じ `event_id` の `Approved` イベントが複数存在する場合、誤って
  反映される件数が 0 件である。
- **SC-003**: 運営担当者が日常の公開更新を手動 CSV 更新なしで完了できる。
- **SC-004**: 定期実行と手動実行のいずれでも、同一入力に対して同一の公開結果が得られる。

## Assumptions

- 管理元データには、公開可否を判定するための `status` 項目が存在する。
- `Approved` が公開対象を示す唯一の状態値である。
- フロントエンドは CSV 形式の公開データを取り込める前提とする。
- データベース化は本機能の対象外とする。
- `event_id` でイベントの同一性を判定できる前提とする。
- 管理元シート / CSV には `start_date` と `end_date` が ISO 形式で存在する前提とする。
- `updated_at` は管理元で必須入力される前提とする。
- 技術スタック、実行基盤、認証方式などの実装詳細は後続の計画フェーズで決定する。

## 用語

- **管理元**: イベント情報を編集・承認する元システム。現時点では Google
  スプレッドシートを含む。
- **承認済み（Approved）**: 公開対象としてユーザー表示を許可された状態。
- **公開対象データ**: 承認済みイベントのみを抽出した、公開に利用可能なデータ。
- **公開用 CSV**: フロントエンドが利用するために整形された CSV 出力。
- **公開用 CSV 正本**: Git 上で管理され、次回同期時の比較元にも使われる公開用 CSV。
- **同一列構成**: Google スプレッドシート管理元と同じ列順・列名で CSV を出力すること。
- **event_id**: 新規保存か既存更新かを判定する識別用 ID。
- **event_name**: 画面表示や説明のためのイベント名称。
- **重複エラー**: 同じ `event_id` の `Approved` イベントが複数あり、対象外として
  扱う状態。
- **チェック対象外**: 公開判定や更新判定を行わず、反映処理の対象から除外すること。
- **反映**: 生成された公開用データを Yosakoi Portal 側の表示に利用可能な状態へ
  更新すること。
